# Flutter Patterns (project-specific)

*Project-specific pattern rulings. Generic Flutter patterns live in the central base (`D:\Documents\Claude\Flutter development knowledge\`). Add entries as patterns are established in code.*

## Established at bootstrap (2026-08-25)

- **Adaptive shell:** `AppAdaptiveScaffold` in `core/widgets/` wraps the `StatefulShellRoute` navigation shell; NavigationBar under 600dp, NavigationRail 600–1199, extended rail ≥1200. Per-screen adaptivity uses `LayoutBuilder` + `Breakpoints` constants.
- **Theme tokens:** semantic colors (cycle phases, intensity zones, success/warning) and spacing/radius scales come from `AppTokens` ThemeExtension — `Theme.of(context).extension<AppTokens>()`. Both brightnesses defined from day one.
- **Settings state pattern (the reference implementation):** `SettingsRepository` (data) over SharedPreferences → `@riverpod` controller (presentation) → screen watches controller. New simple features copy this shape.
- **High-frequency streams (future GPS):** raw sample streams stay out of widget-watched providers; derive throttled/selected providers for UI (see central `ui-performance.md`).

## Established in Phase B (2026-08-26)

- **Drift repository shape (reference: `features/profile/`)**: abstract repo in `domain/`, Drift impl in `data/` wrapping raw errors into `StorageException`; row↔entity mapper lives in the impl file; import the database `as db` to dodge the row-class naming collision; the `@Riverpod(keepAlive: true)` repository provider lives in the feature's `<name>_providers.dart` composition surface typed as the domain interface (ADR 007).
- **Router redirect bridge**: auth/onboarding-style redirects bridge an app-scoped Riverpod `Notifier` to `GoRouter.refreshListenable` via a small `ChangeNotifier`; the `redirect` closure uses `ref.read` (a top-level `ref.watch` would recreate the router on every flip). All redirects stay in `router.dart` (ADR 002).
- **Full-screen flows live OUTSIDE the shell route** (onboarding at `/onboarding`) — no nav chrome; step flows use `switch` + `AnimatedSwitcher`, not PageView (PageView's cache keeps adjacent pages built, breaking `find.text` assertions and semantics).
- **SharedPreferences access**: single `sharedPreferencesProvider` in `core/config/shared_preferences_provider.dart` — never re-declare per feature.
- **Validation as values**: flow/form validation returns typed results (see onboarding controller), exceptions only for failures.

## Established in Phase C wave 1 (2026-08-26)

- **Drift schema migrations (reference: `core/db/app_database.dart` v1->v2, `activities`/`activity_samples`)**: bump `schemaVersion`, override `migration => MigrationStrategy(onCreate: (m) => m.createAll(), onUpgrade: (m, from, to) async { if (from < N) { await m.createTable(newTable); await m.createIndex(idxSomeIndex); } })`. Declare indices with `@TableIndex(name: '...', columns: {#col})` on the table class (drift_dev generates a matching `Index get idxCamelCaseOfName` getter on the generated database base class - the name is a deterministic camelCase of the `name:` argument; run `build_runner build` once and read the generated `.g.dart` to confirm the exact getter before wiring it into `onUpgrade`, rather than guessing). Never edit an already-shipped schema version's table file in place - new columns/tables arrive as a new version + upgrade step.
- **Testing a migration's `onUpgrade` step directly (without a second versioned database class)**: open `AppDatabase.forTesting(NativeDatabase.memory())` (this runs `onCreate` at the *current* version, creating every table), then `DROP TABLE` the ones the migration under test is responsible for adding, then call `database.migration.onUpgrade(Migrator(database), oldVersion, newVersion)` directly. This exercises the exact production SQL of the upgrade step - what's actually at risk of being wrong - without the heavier machinery of a second `@DriftDatabase`-annotated legacy class or drift_dev's schema-snapshot verification tooling. It does not additionally prove drift's own version-detection triggers the callback automatically; that's a much smaller risk (it's drift's tested code, not ours).
- **Drift stream providers + widget tests: "A Timer is still pending" false failure.** Drift's query-stream cleanup schedules a zero-duration `Timer` whenever an autoDispose stream-backed provider (any `@riverpod Stream<...>` watching a Drift `.watch...()` query) loses its last listener. A widget test that navigates through several screens backed by such providers (subscribe -> navigate away -> dispose, repeated) can end with one or more of these timers still unflushed when flutter_test's own end-of-test teardown unmounts the widget tree - which happens *after* the test body returns, so there's no `pump()` left to flush it, and the framework's invariant check fails with "A Timer is still pending even after the widget tree was disposed" (and can then hang until the outer per-test timeout). Fix: end the test by forcing disposal under a pump you control, then pump once more to flush: `await tester.pumpWidget(const SizedBox.shrink()); await tester.pump(const Duration(milliseconds: 1));`. Seen in `test/features/activity_flow_test.dart`.

## Established in Phase C wave 2 (2026-08-26)

- **Platform adapter pattern (reference: `core/platform/location/`)**: freezed value type (`LocationFix`) + abstract adapter with a `capabilities` surface (`canRecordActivities` + honest `reason` for UI) + plugin-backed impl branching on `kIsWeb`/`defaultTargetPlatform` (never `dart:io`) + `@Riverpod(keepAlive: true)` provider. UI gates features on capabilities and shows the reason, never errors.
- **Long-running operation controller (reference: `recording_controller.dart`)**: keepAlive controller owning a pure-domain session object (injected clock, exhaustively unit-testable), with an explicit UI lifecycle enum incl. failure-recovery states (`saveFailed` + `retrySave()` keeps the finished result in memory — a persistence failure must never lose user work), `reset()` for re-entry (keepAlive state is forever unless you reset it — B1 bug class), epoch-token guards on every `await` in `start()`-style methods (re-entrancy + cancel-during-await).
- **Plugin `Position`-style values**: gate on `has*` flags before mapping to nullable fields — unmeasured reports as 0.0.

## Established in Phase D (2026-08-27)

- **Derived-data provider (reference: `features/streaks/`)**: no data/ layer at all — a pure engine in domain/ + a composition-surface stream provider combining other features' surfaces via `core/utils/combine_latest.dart`. Disposal rule learned the hard way: stream-cleanup `onCancel` must be fire-and-forget (`unawaited`), never awaited — awaited Drift cancels wedge widget-test teardown for 10 minutes (central testing-pitfalls.md 2026-08-27 entry).
- **Any widget test that pumps the full `App()` must end with the Drift timer-flush pattern** (`pumpWidget(SizedBox.shrink())` + one pump) — the home screen's streak chain subscribes to Drift streams on every app boot, so this now applies to ALL full-app tests, not just data-heavy ones.

## Established 2026-09-03

- **Bottom sheets: always `showAppBottomSheet`** (`core/widgets/app_bottom_sheet.dart`), never `showModalBottomSheet` directly — `test/app/modal_sheets_use_root_navigator_test.dart` is a source scan that fails on any direct call outside that file. The wrapper is where `useRootNavigator: true` (shell-branch clipping) and the **system nav-bar inset** are decided once. Edge-to-edge is mandatory on Android 15, and Flutter's `useSafeArea: true` only guards the *top* (`SafeArea(bottom: false)` inside `ModalBottomSheetRoute`) — nothing pads the bottom, so before this every sheet's last row sat under the 3-button nav bar (found on device: the Wellbeing day sheet's "Mark as a recovery day"). The wrapper pads by `max(viewPadding.bottom, viewInsets.bottom)`: `viewPadding` not `padding`, because `padding` is already net of `viewInsets` and collapses to zero while the keyboard is up; `max` not sum, because the nav bar is drawn *over* the IME. It then `MediaQuery.removePadding(removeBottom: true)`s, so a sheet that still wraps itself in `SafeArea` gets a no-op instead of a double gap — **sheets add no bottom padding of their own**. The padding sits outside the sheet's child, so a scrolling sheet gets a shorter viewport and its last row scrolls to rest above the bar.
- **Bottom-anchored content on full-screen routes**: `Scaffold` insets the `floatingActionButton`, `bottomNavigationBar` and `persistentFooterButtons` slots for you (the FAB via `ScaffoldPrelayoutGeometry.minViewPadding`, the footer via its own `SafeArea(top: false)`). It does **not** inset content you pin at the bottom of `body` yourself — a `Column` ending in a button row, `Positioned(bottom: 0)`, `Align(bottomCenter)`. Every non-shell screen in this app currently roots `Scaffold.body` in a `SafeArea`, which is what makes them safe; keep that convention rather than relying on Scaffold.
- **`contentMaxWidth` (560) is a one-column reading width, not a page width.** A multi-column layout must *widen* the cap (`contentMaxWidth * columns + spacing`), never split it - a naive `ConstrainedBox(maxWidth: contentMaxWidth)` around a two-column grid leaves the second column unreachable on every window. `HomeScreen` measures the *window* in a `LayoutBuilder`, decides the column count from `Breakpoints`, then caps to the matching width and passes `twoColumn` down as a parameter (`home_card_layout.dart`) so the child does not re-measure the already-capped box. Cards of unequal height go in per-column `Column`s, not a `GridView` (a shared aspect ratio is what overflowed the old Home grid under text scale).
- **`ReorderableListView`: use `onReorderItem`, not `onReorder`** - `onReorder` is deprecated in Flutter 3.47 and fails `--fatal-infos`; the new callback pre-adjusts `newIndex`, so do no index arithmetic. **`SegmentedButton` overflows rather than shrinking** - three segments at 150% text are wider than a 320dp dialog; wrap it in a horizontal `SingleChildScrollView`. Both from the yoga sequence editor (2026-09-04).
