## Beyond the matrix — existing assets the spec maps onto

- **Fitness profile (§5.1): IMPLEMENTED** (S1-3, 2026-08-28) — schema v7: DOB, height, weight (unit-aware entry incl. ft+in/lb, canonical metric, S2 handling), fitness goal, running/strength experience, training days; `ageOn` derivation (leap-day-tested); all optional; skippable onboarding step. Nutrition goals/BMR/TDEE landed with S1-4 (2026-08-28): the profile's height, weight and DOB now feed `estimateEnergyNeedsForProfile`, and the nutrition goals screen links back here by name when any of them is missing.
- **Recovery-day management (product-owner request, 2026-08-28)**: protected streak card opens a "Today" sheet listing active protection sources with per-source actions (remove recovery day + undo, wellbeing/cycle links); wellbeing history interleaves recovery days with remove; retroactive "Mark a recovery day" (date-picked, streak heals). Debugging surfaced one production bug (snackbar-undo `ref`-after-unmount — fixed with capture-before-unmount) and three new central testing pitfalls (real-zone snackbar timers, scoped date-picker fields, BackButton vs pageBack).
- **Women's health profile (§5.2): PARTIAL** — separation already architectural (cycle data isolated, S3 rules); today only cycle tracking + streak-pausing toggle exist. Life-stage modes (contraception/peri/menopause/pregnancy/postpartum) are Stage 4 by the spec's own staging.
- **Privacy (§18.4, §30–32)**: strongly aligned and enforced — tier system (S0–S3), no-sensitive-logging rule (review-verified every phase), delete-my-data (cycle first), local-first, no analytics at all yet. Export is a known gap (deferred registry: cycle-data export FIRST).
- **Domain-out-of-UI (§36)**: already the architecture (pure engines: recording, streaks, track analysis, period days; ADR 007 composition surfaces). Spec-suggested services map onto existing/planned pure domain modules — no service-class refactor needed.
- **Testing (§33)**: 376 tests incl. contested engine tests, migration tests, guard tests; the spec's streak/cycle test lists are largely covered for what exists.
- **Explicitly-not-required (§27)**: social was already sequenced last in our roadmap — aligned.
- **Home dashboard (§20–21)**: partial — greeting + streak hero + Progress card; becomes the "Today" decision surface as check-in/plan pieces land (full version needs Stage 2 plans).

## Spec-alignment decisions taken with this audit

1. **Vision reframe adopted**: women-first fitness platform, not period-first — `product_vision.md` updated; cycle features remain optional/modular (already opt-in).
2. **Adaptive streak evolution accepted** as the next engine change (Stage 1): `DayStatus`-based with protected recovery; the current pure/retroactive engine is the right substrate — this is an extension, not a rewrite.
3. **Period-pausing toggle — recommendation for product owner**: keep it, reframed. It is opt-in (user-controlled, not automatic in the §5.8 sense) and shipped; recommend it becomes "treat logged period days as protected recovery" — one voluntary source among several, default OFF for new users once symptom-driven protection exists (today it defaults ON as the only mechanism). Flagged, not silently changed.
4. **Prediction stance unchanged where it matters**: predictions gain a feature (§5.4 estimator) but still never pause streaks, never auto-adjust anything (§8.5 "do not move sessions solely because a predicted date arrived" — consistent with our existing rule).

## Smallest coherent Stage 1 sequence (proposed — preserves architecture)

Ordered to complete the §45 core loop first (check-in → context → decision → protected streak → activity → history), then the missing pillars:

1. **S1-1 Daily check-in + flare logging** — new feature, two tables (daily_checkins, flare_events), fast opt-in check-in UI, flare log with severity/impact/no-diagnosis categories; cycle events can reference the same symptom vocabulary. (Schema v5)
2. **S1-2 Protected streak evolution** — `DayStatus` engine rework: completedActivity / protectedRecovery (flare impact "unable to train" + explicit user recovery action + optionally period days per toggle) / unscheduled; recovery-decision prompt when a check-in reports significant symptoms ("Keep today / Recovery"); home card language per §5.9 (positive, never "excused/failed").
3. **S1-3 Fitness profile expansion** — DOB/height/weight/goals/experience/training days (+ migration); powers BMR/TDEE later; height/weight S2 handling.
4. **S1-4 Nutrition core — DONE (2026-08-28)** — food diary (meals, custom foods, servings), calorie/macro totals, targets, ED-safe presentation; local BMR/TDEE estimates clearly labelled. Shipped as described in the Nutrition row above. Decisions recorded in `domain/nutrition.md` and gated by `research/nutrition_energy_estimates.md`; no ADR needed (no new package, no new architectural mechanism). Two things worth carrying forward: the hide-calorie-numbers preference is scoped to the **diary** (the goals screen still shows the calorie target field and the estimate, since that is where the number is set and where the preference itself lives), and a diary entry deletes without a confirmation step — unlike routes and flares — because a logged food is trivially re-loggable and a confirmation dialog around removing food is friction this feature specifically does not want.
5. **S1-5 FoodDataProvider + barcode** — provider abstraction, Open Food Facts impl, local product cache, mobile barcode scan (scanner package evaluation), name search everywhere.
6. **S1-6 Gym/strength logging** — exercise catalogue (seeded, fresh ids), templates vs sessions, set logging (weight/reps/optional RPE), history; sessions count as `completedActivity`.
7. **S1-7 Local cycle prediction** — range + variability + confidence from history; honest low-confidence UI for irregular cycles; disclaimers per §3.

Each step is independently reviewable (implement → Workflow review → fix), extends existing patterns (drift tables per conventions, ADR 007 surfaces, pure domain engines), and requires no rewrite of anything shipped. Stages 2–5 remain roadmap-only per §44 step 9.
