# Android Build

## Gradle PKIX SSL failure — RESOLVED 2026-08-27

**Symptom (2026-08-26 → 2026-08-27):** every Gradle artifact download failed with `PKIX path building failed: unable to find valid certification path to requested target`, against both dl.google.com and repo.maven.apache.org. Android compile validation was deferred on this machine for a day because of it.

**Root cause (measured, not inferred):** **Avast Antivirus "Web/Mail Shield" HTTPS scanning.** A probe JVM that completes a handshake and prints the top of the served chain reports:

```
chain top issuer: CN=Avast Web/Mail Shield Root, O=Avast Web/Mail Shield,
                  OU=generated by Avast Antivirus for SSL/TLS scanning
```

Windows trusts that CA (hence browsers and pub.dev working fine), but no JVM's bundled `cacerts` does. Nothing about the project caused it; it would break any Gradle build on this machine.

**Fix — two parts, both required**, in `%USERPROFILE%\.gradle\gradle.properties` (user-level, machine-specific, deliberately NOT committed; a `.bak-2026-08-27` copy of the pre-change file sits beside it):

```properties
org.gradle.java.home=C:/Program Files/Java/jdk-17
org.gradle.jvmargs=-Xmx8G -XX:MaxMetaspaceSize=4G -XX:ReservedCodeCacheSize=512m -XX:+HeapDumpOnOutOfMemoryError -Djavax.net.ssl.trustStoreType=Windows-ROOT
```

1. `trustStoreType=Windows-ROOT` makes the build JVM consult the OS trust store, which already contains Avast's CA. **This is not a security downgrade** — certificate validation stays fully enabled; only the source of trust anchors changes. (Disabling verification would be a downgrade; this is not that.)
2. `org.gradle.java.home` is required because **Android Studio's bundled JBR cannot load `Windows-ROOT`** — it dies with `NoSuchAlgorithmException: Error constructing implementation (algorithm: Default, provider: SunJSSE ...)`. A full JDK loads it fine. Verified against `C:\Program Files\Java\jdk-17`.

> **Gotcha:** `GRADLE_USER_HOME`'s `gradle.properties` **overrides** a project's own, and `org.gradle.jvmargs` is replaced wholesale, not merged. The memory flags above are therefore copied from `android/gradle.properties`; if that project file changes them, the user-level file must change too or the project's values are silently ignored.

**Diagnostic that settles it in one run:** a single-file Java probe (`java TlsProbe.java`) that opens an `HttpsURLConnection` to the Maven repos, prints the response code, and prints the issuer of the top certificate in the chain. Whoever signs the chain root is the interceptor. Run it under each candidate JVM, with and without `-Djavax.net.ssl.trustStoreType=Windows-ROOT`, to isolate *which* JVM and *which* truststore works — far faster than reading Gradle stack traces.

## Two further blockers hit immediately after, both now fixed

**1. `Could not close incremental caches ... class-fq-name-to-source.tab`** on `:shared_preferences_android:compileDebugKotlin`. Kotlin's incremental-compilation cache files get held open on Windows — real-time AV scanning is the usual culprit, and this machine runs Avast. Survived a `flutter clean`. Fixed with `kotlin.incremental=false` in `android/gradle.properties`. Costs a full recompile of plugin modules per build; a slower build beats one that cannot finish.

**2. `Failed to find target with hash string 'android-37'`.** `permission_handler_android` requires compileSdk 37, and the SDK manager installs API 37 under Android's new **minor SDK versioning** as `platforms/android-37.0` (`source.properties` → `AndroidVersion.ApiLevel=37.0`). A plain `compileSdk = 37` builds the hash string `android-37` and misses it. Fixed in `android/app/build.gradle.kts` with the AGP 9 minor-version pair:

```kotlin
compileSdk = 37
compileSdkMinor = 0
```

Do **not** "fix" this by pinning `compileSdk = 36` — that trips `checkDebugAarMetadata`, because permission_handler demands 37. AGP 9.0.1 also warns that its maximum *recommended* compileSdk is 36; the build succeeds regardless.

## Current status (2026-08-27)

`flutter build apk --debug` and `flutter build apk --release` both succeed (release APK ~63.7 MB). Android is no longer a deferred target on this machine — on-device GPS testing of the recording and route features is now possible. iOS still needs macOS.

**If Avast HTTPS scanning is ever disabled**, the user-level block can be removed wholesale; the alternative permanent fix is to exclude Java/Gradle from Avast's HTTPS scanning, or import Avast's root CA into the JDK truststore (needs admin; a system security change, so it is the user's call, not an agent's).

## Release build fails at `:app:minifyReleaseWithR8` with ML Kit "Missing class" — RESOLVED 2026-09-03

**Symptom:** `flutter build apk --release` failed at `:app:minifyReleaseWithR8`:

```
Missing class com.google.mlkit.vision.text.chinese.ChineseTextRecognizerOptions
Missing class com.google.mlkit.vision.text.devanagari.DevanagariTextRecognizerOptions
Missing class com.google.mlkit.vision.text.japanese.JapaneseTextRecognizerOptions
Missing class com.google.mlkit.vision.text.korean.KoreanTextRecognizerOptions
```

`flutter build apk --debug` and every debug smoke build had passed cleanly — this only showed up when release was built for the first time after adopting `google_mlkit_text_recognition` (ADR 012, feat/nutrition OCR).

**Cause:** `google_mlkit_text_recognition`'s Android plugin code references the optional Chinese/Devanagari/Japanese/Korean recogniser option classes so a host app can opt into those scripts. MenFit bundles only the Latin model on purpose (ADR 012). Debug builds don't run R8, so the missing classes are never noticed. Release builds run R8 in full mode, which treats any referenced-but-absent class as an error unless told otherwise.

**Fix** (`android/app/proguard-rules.pro`, new file):

```proguard
-dontwarn com.google.mlkit.vision.text.chinese.**
-dontwarn com.google.mlkit.vision.text.devanagari.**
-dontwarn com.google.mlkit.vision.text.japanese.**
-dontwarn com.google.mlkit.vision.text.korean.**

-keep class com.google.mlkit.vision.text.latin.** { *; }
```

and wiring it into `android/app/build.gradle.kts`'s `release` build type:

```kotlin
release {
    signingConfig = signingConfigs.getByName("debug")
    proguardFiles(
        getDefaultProguardFile("proguard-android-optimize.txt"),
        "proguard-rules.pro",
    )
}
```

This is the plugin's documented resolution — the -dontwarn lines don't disable shrinking or affect the bundled Latin recogniser, they just tell R8 the four unbundled classes are intentionally absent. Guarded against accidental removal by `test/platform/android_release_r8_rules_test.dart` (both files look "unused" to a quick read, since nothing debug-built ever exercises them).

**Rule for future adoptions:** any new ML Kit package, or any other package with optional/conditionally-referenced native Android classes, must be smoke-built with `flutter build apk --release` — not just `--debug` — before adoption is considered complete. R8 only runs in release; a clean debug build proves nothing about it. (Folded into `knowledge/engineering/coding_standards.md`'s validation sequence and into the central package-ecosystem notes.)

**Current status note:** the "Current status (2026-08-27)" section above, which says release builds succeeded, predates ADR 012's ML Kit adoption. That statement was true when written; it stopped being true once `google_mlkit_text_recognition` was added and needed the fix documented here. Both debug and release builds pass again as of this fix.

> **APK size note (2026-09-04):** the 63.7 MB release figure above predates the bundled ML Kit Latin model (ADR 012) and the audio/wakelock plugins (ADR 014); the release APK is now 123.0 MB (debug-signed, single universal ABI). Split-per-ABI / App Bundle remains the registered fix.


## Linux checkout after Windows build (2026-11-16)

A first Linux release build failed in `compileFlutterBuildRelease` trying to
create a relative `android/app/D:/Documents/.../arm64-v8a` directory. The copied
`.dart_tool/flutter_build` hook results contained the old Windows project path.
`flutter clean` followed by `flutter pub get` regenerated host-specific build
metadata and moved the retry past that failure. This deletes generated build
artifacts only; do not rewrite source paths or lower Android SDK versions.
The old Windows watchdog is not appropriate on this host.
